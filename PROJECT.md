# Orto-N-L-M — Project Contract

**Актуальность:** 27 октября 2026  
**Продукт:** Orto-N-L-M / Ортона-AI  
**Статус:** веб-приложение развёрнуто в production.

## 1. Назначение продукта

Orto-N-L-M — backend и логика AI-платформы для извлечения практической экспертизы сотрудников и преобразования её в структурированные рабочие процессы. Ортона-AI — основной веб-интерфейс продукта.

Каноническая цепочка:

```text
Должность → Интервью → Process JSON → Инструкция → Обучение → Тест → Результат
```

**Process JSON — канонический источник данных о процессе.** Инструкции и тесты формируются на его основе и не должны становиться независимыми источниками истины.

## 2. Текущая архитектура

- **Frontend:** React / Vite, веб-интерфейс Ортона-AI.
- **Backend:** FastAPI, REST API, аутентификация, авторизация и бизнес-операции.
- **Database:** PostgreSQL, постоянное хранение данных.
- **AI / orchestration:** OpenAI API и n8n для AI-workflows и интеграций.
- **Deployment:** Docker на серверной инфраструктуре, HTTPS через Caddy.

Telegram-интерфейс и workflow — ранний этап развития проекта. Их наличие в репозитории не означает, что Telegram является основным пользовательским интерфейсом текущего продукта.

## 3. Реализованные пользовательские контуры

### Руководитель
- управление должностями;
- работа с инструкциями;
- просмотр результатов тестирования и истории попыток.

### Специалист
- адаптивное AI-интервью;
- текстовые и голосовые ответы с транскрибацией;
- запрос и обработка иллюстративных материалов в рамках интервью;
- формирование и сохранение Process JSON;
- генерация инструкции;
- работа со своими процессами.

### Стажёр
- выбор должности и инструкции;
- отметка изученных инструкций;
- обучение на основе инструкции;
- тестирование по Process JSON;
- сохранение результатов и восстановление прогресса.

Эти сценарии проверены владельцем проекта в работающем приложении. Документ не заменяет проверку текущего production-окружения.

## 4. Источник знаний и незавершённые возможности

В компании пока нет сформированной корпоративной базы знаний. Поэтому функции, требующие такого источника, не считаются реализованными:

- поиск по полноценной базе знаний;
- ответы на произвольные вопросы на основе корпоративных документов;
- полноценный RAG / AI knowledge assistant.

Это осознанная граница текущего объёма, а не неисправность уже работающих пользовательских сценариев. Эти возможности могут быть добавлены после подготовки и согласования источника знаний.

## 5. Данные и безопасность

Основные сущности приложения включают пользователей и роли, должности, процессы и Process JSON, файлы, сессии интервью, результаты тестов и отметки об изучении инструкций.

- Проверки ролей и доступа должны выполняться на backend.
- Frontend не является границей безопасности.
- Секреты, токены, пароли, JWT secrets и production connection strings нельзя хранить в публичном репозитории.
- Рабочие экспорты n8n перед публикацией должны быть очищены от живых токенов и credentials.

## 7. Инженерные правила

1. Не переписывать подтверждённо работающую архитектуру без объективной технической причины.
2. Перед изменением workflow сверять его с актуальным экспортом и серверным окружением.
3. Не объявлять функцию реализованной только потому, что она описана в roadmap.
4. Не считать отсутствие базы знаний ошибкой приложения, если соответствующая возможность намеренно отложена.
5. Не публиковать production-секреты.
